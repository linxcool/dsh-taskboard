# 工作流走查：从建卡到验收

- 日期：2026-11-09
- 目的：把「员工绑定 + 会话可见性 + 六列看板」放进真实操作里跑一遍，标出断点，并把断点补进 spec / plan
- 相关：`2026-11-09-employee-binding-design.md`、`2026-11-09-github-status-columns-design.md`

图例：✅ 现有能力；🆕 本设计新增；⚠ 断点（下方编号对应第 6 节）

## 1. 链路 A：新建空白任务 → 选员工 → 开会话 → 验收

| # | 人的动作 | 界面 | 宿主 / 数据 | 状态 |
| --- | --- | --- | --- | --- |
| A1 | 点「＋ 新建任务」 | 建卡表单（双栏） | — | ✅ |
| A2 | 选执行模式（preset） | 角色 chip + 权限初值随之带出 🆕 | 前端读 `ledger.employees` 调 `permissionForCreate` | 🆕 |
| A3 | 看到权限来源 | 「实际生效：📁 可写入工作区 · 来源：员工绑定」 🆕 | 纯前端 | 🆕 |
| A4 | 填标题 / 描述 / Prompt / 验收清单 | — | — | ✅ |
| A5 | 选执行方式：新建会话 / 复用 | 下拉 🆕 | 写 `execution.reuseSessionId` / `sessionReuseMode` | 🆕 |
| A6 | 点「创建任务」 | 表单关闭，卡出现在**就绪**列 | `POST /tasks` → status `todo`，`permission` 由 `permissionForCreate` 决定 | ✅ + 🆕 |
| A7 | 点卡片上的「＋ 开会话」（没有会话时） | 弹层：preset / 权限 / 分支 + 可编辑用户正文 🆕 | `GET /tasks/:id/opening-body` 取正文 | 🆕 |
| A8 | 改正文，点「发送并创建会话」 | 弹层关闭；卡片转**执行中**，出现 `🤖 xxxx ↗` | `POST run`（带 `openingBody`）→ 建执行记录、`status=in_progress`、注入框架行 + 用户消息 | 🆕 |
| A9 | 等待 agent 干活 | 卡片留在执行中；SSE 推送评论/清单变化 | agent 用 `taskboard_*` 更新卡片 | ✅ |
| A10 | agent 交接到待你验收 | 卡进入**待你验收**，显示报告与清单 | agent `taskboard_move → in_review` | ✅ |
| A11 | 人点「✓ 完成」 | 卡进**完成** | `done` 只允许人；门禁检查未关闭的评审卡 | ✅ |

断点：**A6→A7 之间卡是「就绪」但没有会话**，这一步现在没有提示“下一步该开会话”，新用户会停在原地。见 ⚠G1。

## 2. 链路 B：从员工目录建卡（本设计的主入口）

| # | 人的动作 | 界面 | 宿主 / 数据 | 状态 |
| --- | --- | --- | --- | --- |
| B1 | 工具栏「👥 员工」 | 目录四态：已绑定启用 / 停用 / 未分配 / 失效 🆕 | 读 `ledger.employees` + preset catalog | 🆕 |
| B2 | 点某执行员工的「使用这位员工建卡」 | 建卡表单，preset / 角色 / 权限已带出 | 纯前端 | ✅→🆕 |
| B3 | 勾「⚡ 立即执行」并保存 | 卡直接进执行中并开跑 | 保存后立刻 `run`（不预览正文） | ✅ |
| B4 | 不勾「立即执行」保存 | 卡进就绪，等人工触发 | 同 A6 | ✅ |

断点：
- **B2 用的是评审员工时**：按钮仍然叫「使用这位员工建卡」，建出来的是普通卡，不关联任何源任务——与用户对「评审员工」的预期相反。见 ⚠G2。
- **B3 与 A7 是两条不同路径**（一个有预览、一个没有），界面上没有任何文字说明差别。见 ⚠G3。
- 目录里改绑定后，已有卡片不受影响，但目录没有任何提示。见 ⚠G4。

## 3. 链路 C：GitHub Issue 导入 → 分配员工 → 开跑

| # | 人的动作 | 界面 | 宿主 / 数据 | 状态 |
| --- | --- | --- | --- | --- |
| C1 | 外部同步拉 issue | 卡进**待澄清**或**就绪**（按导入目标设置，默认待澄清） | `POST /sync` → `permission` = 看板默认（此时还没有员工） | ✅ |
| C2 | 打开卡片，想把这张卡交给某个员工 | 详情页只有「编辑」，没有「执行员工」入口 | — | ⚠G5 |
| C3 | 进编辑表单改 preset | 保存后 `presetId` 变了 | 但 `permission` 仍是导入时写的看板默认，**不会**按新绑定重算 | ⚠G6 |
| C4 | 回到卡片点「＋ 开会话」 | 同 A7 | 同 A8 | 🆕 |
| C5 | 执行完 → 待你验收 | 与 A10 相同 | 若配置了回写，Project Status 同步 | ✅ |

## 4. 链路 D：发起评审 → 评审卡执行 → 门禁放行

| # | 人的动作 | 界面 | 宿主 / 数据 | 状态 |
| --- | --- | --- | --- | --- |
| D1 | 在源卡（执行中/待你验收）点「🧪 发起评审」 | 建卡表单预填评审标题/描述/Prompt | — | ✅ |
| D2 | 保存 | 评审卡进**就绪**，带 `reviewOf` 与只读权限 | `presetId` = 默认评审员工（★） 🆕 | 🆕 |
| D3 | 评审卡上「＋ 开会话」→ 发送 | 评审会话开跑 | 只读权限；框架行 + 评审正文 | 🆕 |
| D4 | 评审卡完成 → 待你验收 | 源卡详情显示「评审未完成」解除 | 门禁读未关闭评审卡 | ✅ |
| D5 | 验收评审卡 → 完成 | 源卡「✓ 完成」恢复可点 | — | ✅ |

断点：**D2 之后评审卡与源卡同在「就绪」列**，只有一个小 chip 区分；评审卡被误当普通卡执行也不会有人拦。见 ⚠G7。

## 5. 链路 E：定时任务（无人工介入）

| # | 事件 | 宿主 | 数据 | 状态 |
| --- | --- | --- | --- | --- |
| E1 | cron 到点 | scheduler 选中 `todo` 卡 | — | ✅ |
| E2 | 启动执行 | `run(trigger='scheduled')`，闸门只接受 todo | 卡转执行中 | ✅ |
| E3 | 完成 | 按 `periodicCompletion` 回到待办或新建下一轮 | — | ✅ |

断点：定时卡用的是**建卡时写下的** preset 与权限。目录里后来改了绑定，定时卡不会跟着变——这符合「绑定只影响新任务」，但同样缺提示（并入 ⚠G4）。

## 6. 断点清单与处理

| 编号 | 断点 | 影响 | 处理 | 归属 |
| --- | --- | --- | --- | --- |
| G1 | 「就绪」卡没有会话时，下一步该做什么没有引导 | 新用户停住 | 卡片会话槽位在无会话时显示虚线 `＋ 开会话`（已有设计），并在空态弹层顶部说明「发送后卡会进入执行中」。spec 已含，**补一句空态文案** | 员工绑定 spec §7.5 |
| G2 | 评审员工的「使用」按钮会建出普通卡，语义相反 | 误解 | 评审员工的按钮改为「用它发起评审」：点击后先选源任务（进行中/待你验收），再打开预填表单；没有候选源任务时禁用并提示 | 员工绑定 spec §7.1、plan Task 6 |
| G3 | 「立即执行」与「开会话」两条路径差别不可见 | 预期落空 | 表单里「⚡ 立即执行」旁加一行说明「= 不预览，直接用生成的正文发送；想先改正文就用卡片上的『＋ 开会话』」 | 员工绑定 spec §7.2 |
| G4 | 目录改绑定不影响已有卡片，界面无提示 | 误以为生效 | 员工目录页脚加常驻提示：「绑定只影响之后新建的任务；已有卡片按各自记录的 preset 与权限执行」 | 员工绑定 spec §7.6 |
| G5 | 存量卡（含导入卡）没有「执行员工」入口，只能进编辑表单 | 链路长 | 详情页新增「执行员工」下拉（读绑定表 + preset catalog），改完立即写入任务 `presetId`；权限按 G6 规则处理 | 员工绑定 spec §7.3、plan Task 7 |
| G6 | 换 preset 不改权限，绑定对存量卡失效 | 权限与员工不一致 | 规则：编辑时若当前 `permission` 等于「原绑定权限或看板默认」，则按新绑定重算；否则保留（用户显式设过） | 员工绑定 spec §6、plan Task 7 |
| G7 | 评审卡与普通卡同列，只有 chip 区分 | 误操作 | 评审卡的卡片加左侧色条（`data-role="review"`）+ 标题前置「评审：」已有；不改列，避免第七列。**暂不新增存储**，只做视觉区分 | 员工绑定 spec §7.4 |

### 6.1 明确不补（记录原因）

- **会话列表里“继续这个会话跑任务”**：续跑已有「↻ 续跑」入口在详情页，列表只负责定位与跳转，不叠第二套启动语义。
- **一卡多员工轮换**：任务级 preset 是既有模型，换员工就是换 preset；不做 per-round 员工分配。
- **评审结论字段（PASS/FAIL）**：现在依赖 agent 报告与评论，属于 P4 的后续项，不在本次范围。

## 7. 走查结论

链路本身能走通：**建卡 → 开会话 → 执行 → 交接 → 人验收** 五步没有断点；缺口集中在三处：

1. **评审员工的语义**（G2）——最容易被误解，必须改。
2. **存量卡与导入卡的员工分配**（G5 + G6）——否则绑定只对“从目录新建”的卡生效，而看板里大多数卡是导入或手建的。
3. **两条启动路径的可见差别**（G3）与**绑定作用域的提示**（G4）——都是文案级补充。

G1、G7 是观感问题，按上面处理即可，不改变数据模型。
